# 现场记录

上线前后攒的，随手记的，别当规格看；口径以 README 为准。

- 搜索上线当天出了个大笑话：新索引把「北京大学」也召回了。正文里这个词被切成单字入库，查询侧的
  「北京」和「大学」都能命中，用户搜「北京大学」，跳出来一堆只有「北京」或者只有「大学」的页面。
  复盘结论很直白：词典里写着的长词必须整词切出来，切碎了召回就失控。
- 同一批反馈里还有「南京市长江大桥」：切成了 南京 / 市 / 长江 / 大桥 也算对，但和 南京市 /
  长江 / 大桥、南京市 / 长江大桥 都能对上；几种切法词数差不多，谁也不服谁。后来定下来的口径是
  先比词数、再比单字词、最后比词频和，实在分不出就取正向那一种。
- 词频那列本来是运营随手填的，出过两次事之后统一了：重复词条取最大的那个，不按文件顺序谁先谁后。
- 未登录这块也吃过亏：英文和数字整串留着（`iPhone15` 里的 `iPhone` 是词表里的词，得先认出来），
  生僻字、全角字母数字一律逐字切；没人敢让它们再拼成长词，拼错了比切碎还难查。
- 偏移是给前端高亮用的，必须按整篇算，空白也要占位。之前按「去掉空格的正文」算过一次，页面上的
  高亮整体偏移了十几个字，排查了一下午。
- 同一份正文跑两遍必须一模一样，不然两份结果没法逐行比对；别用集合的遍历顺序，别读系统时间。
- 大词表那次 OOM：图省事把 30 万条词读成字符串数组再线性扫，机器直接卡死。这次内存上限写在
  README 里，自己看着办。
- 效果验收是拿 `samples/expected/` 里的期望文件逐行对的：偏移对得上、词面拼得回去，才算过。
- 这回还要顺手做个页面，把切完的词按类型标色排出来，鼠标放上去看它在原文里的起止位置，旁边写上
  这次用到的词典规模和切分耗时。业务方要拿它复核那次召回事故，所以分段和位置只能取自引擎的输出，
  页面里不许另算一遍。
